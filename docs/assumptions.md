# Assumptions and decisions for IT Lead review

Each item: what we assume, why, the alternative, and the impact if it changes.
Status values: **Open** (needs IT Lead), **Confirmed**, **Rejected**.
Items marked ⚠ block or strongly shape the first backlog steps.

## Confirmed by product owner (2026-11-10)

| ID | Decision |
|---|---|
| C-01 | First scope: fund/share class characteristics, fees and costs, daily NAV. |
| C-02 | A client is an asset manager. FinFiles hosts one installation on its own Linux servers. |
| C-03 | Morningstar APIs are the preferred first real provider; other providers will follow. |
| C-04 | Fundscreener is built with PHP/Laravel. It integrates only through the delivery API. |
| C-07 | Stack: **Laravel (`web`) + Java service (`core`)**, replacing the Python default. `core` = ingestion, raw store, normalisation, golden copy; `web` = delivery API, web interface, exports, users. Chosen by product owner 2026-11-10 because the team maintains Laravel (Fundscreener). |
| C-05 | For the demo, real Morningstar data is fetched through the Morningstar MCP connector (available to Claude, not to the application). It is saved as provider files in `demo_data/morningstar/` (git-ignored) and ingested by a file connector. Tests and CI stay on synthetic data. Approved by product owner, 2026-11-10. |
| C-06 | Backlog step 1 (repository skeleton) approved, 2026-11-10. |

## Open

| ID | Topic | Assumption | Alternative | Impact if changed | Status |
|---|---|---|---|---|---|
| A-01 ⚠ | Split of the two services | Product owner chose Laravel + Java (C-07). IT Lead to confirm the split and that the team can maintain, patch and on-call two stacks. The brief asked for a single application; this is a deliberate deviation. | Laravel only (one codebase; Java only if a measured need appears). | Two build pipelines, two dependency audits, two images to patch. | Open |
| A-02 | Standard names | Canonical codes are our own (`fees.ongoing_charges`) with a mapped `standard_ref` to EMT/EPT/EET/openfunds, rather than using standard field IDs as primary keys. Field refs are filled from the official, licensed spec documents. | Use openfunds IDs as primary codes. | Catalogue rename only, if done early. | Open |
| A-03 ⚠ | Tenancy storage | All provider data (raw, normalised, golden) is stored **inside each client schema**, even when two clients receive the same Morningstar data. Reason: licences and often credentials are per client; strict isolation is simpler to prove. | Shared provider schema, fetched once, with licence filter per client. Saves storage and provider calls but weakens "no query crosses clients". | Schema design of step 2–3. | Open |
| A-04 ⚠ | Isolation mechanism | One PostgreSQL role per client schema; every transaction runs `SET LOCAL ROLE` + `SET LOCAL search_path`; tenant context mandatory in the data access layer; cross-tenant tests in CI. | Separate database per client (stronger, heavier to operate); or row-level security in a shared schema (rejected: brief requires one schema per client). | Step 3. | Open |
| A-05 | Licence granularity | Licence = client × provider × validity period. Optional `scope` for data point groups is in the model but not enforced in the first release. | Licence per data point group / per fund universe from the start. | Resolver and delivery filters. | Open |
| A-06 | Manual corrections | `MANUAL` is first in the global default priority. A correction applies to one entity/data point/effective date. Withdrawing a correction is a new row, not a delete. Correction requires a reason; no four-eyes approval in release 1. | Four-eyes approval before a correction becomes eligible. | Adds approval state to `manual_correction`. | Open |
| A-07 | Config storage | Catalogue, mappings and global priority in YAML files in git (changed by PR, validated in CI). Client and data-point overrides in the database (changed by client admins, audited) so they do not need a deploy. | All rules in DB with an admin UI; or all in git. | Where rules are edited and how they are versioned. | Open |
| A-08 | Raw payload storage | `bytea` in PostgreSQL at first. | Filesystem/object store (e.g. MinIO on own servers) with hash reference in DB. | Backup size; migration path kept open via `raw_payload` abstraction. | Open |
| A-09 | Entity matching | ISIN is the master key for share classes; fund matched by provider fund id + ISIN parent link. Unmatched records go to the exception queue; no fuzzy matching. | Internal master fund register maintained by the client. | Ingestion and exception flows. | Open |
| A-10 | Scheduling | Ingestion and golden copy jobs: Spring scheduler in `core` with ShedLock (PostgreSQL) so only one instance runs a job. Exports: Laravel scheduler + database queue in `web`. | System cron / systemd timers; Redis-backed queues. | Ops model; no change to modules. | Open |
| A-11 | Authentication | Web users: OIDC against FinFiles' identity provider (which one?), MFA enforced there. API clients (incl. Fundscreener): OAuth2 client credentials or hashed API keys, one per client, with expiry and rotation. | Local accounts with password + TOTP. | Access module, step "access control". | Open |
| A-12 | Secrets | Environment variables / Docker secrets on the servers; `.env.example` with placeholders only. Provider credentials per client stored encrypted in DB with a key from the environment, if clients bring their own Morningstar credentials. | External vault (e.g. HashiCorp Vault self-hosted). | Connector config. | Open |
| A-13 | Golden versioning | Golden values are append-only; `superseded_at` is the only column ever updated (by a DB function) to make "current" queries fast. | Pure append-only with a view computing the latest row. | Performance vs. purity; easy to change. | Open |
| A-14 | Export destination | Exports written to an SFTP server or a local folder per client; formats CSV, XLSX, JSON. | Push to client endpoints; email (rejected for data security). | Delivery step. | Open |
| A-15 | Backup & retention | Daily base backup + WAL archiving, restore tested quarterly. Raw payloads retained for the contract duration + 7 years unless provider licence says otherwise; data deleted on offboarding after the agreed period. | Per-client retention settings. | ISMS (A.8.13, A.8.10), provider contracts. | Open |
| A-16 | Fundscreener integration | Fundscreener is PHP/Laravel (C-04). Integration only via the OpenAPI contract; we publish the spec and example Laravel HTTP-client calls. No shared code or database. | Shared PHP client package. | Integration effort only. | Open |
| A-17 ⚠ | Fundscreener tenancy | Fundscreener calls the API with a **client-scoped credential** and sees exactly what that client is licensed for. | Fundscreener as its own consumer with its own licences across clients (would need a separate, non-client data scope). | Licence and access design. | Open |
| A-18 ⚠ | Morningstar | Real Morningstar connector is built **after** the end-to-end flow works on synthetic data, and only once: licence terms allow storing/redistributing to Fundscreener, API documentation is available, and credential handling (FinFiles vs. client credentials) is agreed. Tests never call Morningstar; fixtures are synthetic. | Build against Morningstar sandbox first. | Order of backlog. | Open |
| A-19 | Data residency | All data and backups stay on FinFiles servers in the EU/NL. | — | Hosting. | Open |
| A-20 | Repository & CI | Git repository on FinFiles' existing platform (GitHub / GitLab / Azure DevOps?), CI runs lint, type check, tests, dependency audit (`pip-audit`), secret scan. | — | Step 1 setup. | Open |
| A-21 | Dependency pinning | `core`: Gradle version catalog + dependency locking + `verification-metadata.xml` (checksums). `web`: `composer.lock` committed, `composer audit` in CI; npm `package-lock.json` if front-end assets are built. Docker base images pinned by digest. | Maven with enforcer plugin. | Tooling only. | Open |
| A-22 | Web interface | Laravel Blade, server-rendered, with minimal JavaScript (Alpine.js / htmx if needed). | Livewire or Inertia + Vue/React. | Delivery UI steps. | Open |
| A-27 ⚠ | Schema ownership | `core` owns all migrations (Flyway), including the per-client schema template. Laravel's own tables (users, sessions, API tokens, jobs) live in a separate `web` schema migrated by Laravel. | Laravel migrations for everything; or a separate migrations module. | Step 2–3 tooling. | Open |
| A-28 ⚠ | Communication web → core | `web` reads data tables directly (read-only role) for speed, and sends every change as a command to `core`'s internal REST API (mutual TLS or a shared service token on the internal network). | `web` calls `core` for reads too (cleaner boundary, slower); or a message queue. | Where business rules for corrections and overrides live (always in `core`). | Open |
| A-29 | Versions | Java 21 LTS (or 25 LTS if Spring Boot current major supports it), Spring Boot current stable, PHP 8.4, Laravel current major, PostgreSQL 16. Exact versions fixed in step 1. The local PHP 8.2 (XAMPP) is not used; development runs in Docker. | — | Tooling only. | Open |
| A-23 | Money and numbers | `numeric` everywhere (no floats). Percentages stored as percent (1.25 = 1.25%), conversions in mapping config. | Store ratios (0.0125). | Mapping configs and exports. | Open |
| A-25 ⚠ | Morningstar demo data | FinFiles' Morningstar licence permits storing the MCP data locally for an internal demo; the data stays on FinFiles machines, is not shown to third parties without licence check, and is deleted after the demo. | Demo on synthetic data only. | Must be confirmed before the demo data is fetched (backlog step 12a). | Open |
| A-26 | Local development on OneDrive | The project folder is inside OneDrive. Git and virtual environments in a synced folder can cause file locks and sync conflicts, and OneDrive would sync `demo_data/` (real licensed data). | Move the repository to a non-synced folder (e.g. `C:\dev\`) and push to the git server instead. | Developer setup; recommended before real data is fetched. | Open |
| A-30 | Client-created funds | Values typed in when a client creates a fund are stored as source `CLIENT` and rank **last** in the global default, so provider data takes over once a provider covers the fund. `MANUAL` corrections still rank first. | Rank `CLIENT` first (the client's own funds are authoritative). | Priority default and lineage. | Open |
| A-31 | Universe changes | Data stewards and client admins may add, remove and restore share classes; every change is an append-only `universe_event` and audited. Removal stops collection and delivery (including Fundscreener) from that moment; history stays readable. No approval step in release 1. | Four-eyes approval for removals. | Access control, delivery filters. | Open |
| A-32 | UI design | FinFiles Design System v1.0 layout (topbar with 3 items + tabs, no sidebar). Colours and font follow the **client's Fundscreener theme** (AAIS: teal #004c4c, yellow #f3c000, ABN AMRO Sans with Ubuntu fallback), as asked by the product owner on 2026-11-10. Deviates from the design system's fixed dark-blue topbar. | FinFiles palette for every client. | Theme per client in `web`; reuse Fundscreener theme variables. | Open |
| A-35 ⚠ | Taking data points in-house | Per data point, AAIS can become the leading source ("Manage in-house" = data point override `MANUAL > CLIENT > Morningstar > Provider B`). Morningstar stays fallback where AAIS has no value. Values are never copied from Morningstar into AAIS data. | Copy Morningstar values as a starting point (needs explicit Morningstar licence check); or switch whole groups at once. | Licence, priority rules, Fundscreener content. | Open |
| A-36 | "Go to Fundscreener" | In the prototype the button opens a built-in preview fed by the golden copy. In production it links to the client's real Fundscreener, which shows changes once it reads the delivery API (A-16, F-07). | Embed the real Fundscreener in the platform. | Integration effort. | Open |
